### 1. Evidence Framework & Six-Dimensional Status Vocabulary

To enforce Non-Negotiable Rules 2.4 ("Evidence-first reporting") and prevent premature quality claims, every registered application screen is assessed across six distinct architectural dimensions using strict, non-ambiguous status tokens:

| Dimension | Permitted Status Values & Definitions |
|---|---|
| **1. Visual/UI Status** | • `NOT_IMPLEMENTED`: No UI code exists.<br>• `STRUCTURE_ONLY`: Empty scaffolding or unstyled container.<br>• `UI_SIMULATION`: Visually complete prototype or card simulation with mock/hardcoded data.<br>• `FUNCTIONAL_UI`: Production-styled view with dynamic layouts, tokens, and asset bindings.<br>• `VERIFIED_UI`: Visually audited against design specs with 0 developer artifacts. |
| **2. Interaction Status** | • `NOT_IMPLEMENTED`: Zero event handlers or interactive elements.<br>• `STATIC`: Read-only text and cards without interactive controls.<br>• `LOCAL_STATE_ONLY`: Client-side React `useState` state transitions only; resets on reload.<br>• `FUNCTIONAL_INTERACTION`: Full optimistic state updates, forms, validation, and navigation.<br>• `VERIFIED_INTERACTION`: End-to-end verified interactions on target viewport/device. |
| **3. API Integration** | • `NOT_AVAILABLE`: No backend API exists or is defined in contracts.<br>• `NOT_CONNECTED`: API exists but screen does not execute network fetch.<br>• `PARTIALLY_CONNECTED`: Some calls live (e.g. auth/profile) while domain data is mocked.<br>• `CONNECTED`: Screen executes live HTTP/WebSocket requests to all required endpoints.<br>• `VERIFIED_INTEGRATION`: Contract-tested, error-handling verified, token refresh tested. |
| **4. Backend Engine** | • `NOT_IMPLEMENTED`: No business logic, controller, or services in `apps/api`.<br>• `PARTIALLY_IMPLEMENTED`: Data models or stubs exist without complete service logic.<br>• `IMPLEMENTED`: Full Fastify route, service, and transactional logic implemented.<br>• `VERIFIED_BACKEND`: Unit and integration tested backend services with DB rollback. |
| **5. End-to-End Status** | • `NOT_TESTED`: No automated E2E test or manual verification recorded.<br>• `BLOCKED`: Missing dependency (e.g. real database schema, payment gateway) blocks test.<br>• `FAILED`: Automated or manual test failed with regression.<br>• `PARTIALLY_VERIFIED`: Partial journey verified (e.g. login works, checkout simulated).<br>• `VERIFIED`: Complete user journey verified from entry to database persistence. |
| **6. Evidence Level** | • `NONE`: No evidence available.<br>• `SOURCE_ONLY`: Source code verified on disk.<br>• `SCREENSHOT_CAPTURED`: Genuine screenshot captured from running server instance.<br>• `AUTOMATED_TESTED`: Vitest unit/contract/component test verified passing.<br>• `DEVICE_VERIFIED`: Physically verified on real iOS/Android hardware. |
