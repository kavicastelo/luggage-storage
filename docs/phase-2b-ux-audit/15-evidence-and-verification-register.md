### 1. Canonical Eight-Dimensional Status Vocabulary

Every screen is independently audited across eight functional, architectural, and operational dimensions using strict, non-ambiguous status tokens:

| Dimension | Permitted Status Values & Definitions |
|---|---|
| **1. Specification (`Spec`)** | • `SPEC_NOT_FOUND`: No requirement exists in project documentation.<br>• `SPEC_PARTIAL`: Incomplete user stories or missing acceptance criteria.<br>• `SPEC_DEFINED`: Fully documented in FRS, UX Registry, and Workflow matrices.<br>• `SPEC_APPROVED`: Formally signed off by Product Owner (`DOC-UX-P2B-016`). |
| **2. Visual/UI Status (`UI`)** | • `NOT_IMPLEMENTED`: No UI component exists.<br>• `STRUCTURE_ONLY`: Empty container, placeholder text, or incomplete scaffolding.<br>• `UI_SIMULATION`: Visually complete prototype or card simulation with mock data and leaked developer tracking codes (`PW-001`, `HD-008`, `WF-xxx`).<br>• `FUNCTIONAL_UI`: Production-styled view with dynamic layouts, tokens, and asset bindings; zero leaked developer tags.<br>• `VERIFIED_UI`: Visually audited against design specs across all target viewports. |
| **3. Interaction Status (`Interaction`)** | • `NOT_IMPLEMENTED`: Zero event handlers or interactive elements.<br>• `STATIC`: Read-only text and informational cards without interactive inputs.<br>• `LOCAL_STATE_ONLY`: Ephemeral React `useState` state transitions only; resets on page reload.<br>• `FUNCTIONAL_INTERACTION`: Full optimistic state updates, forms, validation, and navigation.<br>• `VERIFIED_INTERACTION`: End-to-end verified interactions on target viewport and real device. |
| **4. API Integration (`API`)** | • `NOT_AVAILABLE`: No backend API exists or is required (e.g. static content).<br>• `NOT_CONNECTED`: API exists but screen does not execute network fetch (uses mock object).<br>• `PARTIALLY_CONNECTED`: Some calls live (e.g. session/auth) while domain data is mocked.<br>• `CONNECTED`: Screen executes live HTTP/WebSocket requests to all required endpoints.<br>• `VERIFIED_INTEGRATION`: Contract-tested, error-handling verified, token refresh tested. |
| **5. Backend Engine (`Backend`)** | • `NOT_REQUIRED`: Static content; no server logic needed.<br>• `NOT_IMPLEMENTED`: No business logic, controller, or services in `apps/api`.<br>• `PARTIALLY_IMPLEMENTED`: Data models or stubs exist without complete service logic.<br>• `IMPLEMENTED`: Full Fastify route, service, and transactional logic implemented.<br>• `VERIFIED_BACKEND`: Unit and integration tested backend services with DB rollback. |
| **6. Database Persistence (`DB`)** | • `NOT_REQUIRED`: Static content; no database persistence needed.<br>• `NOT_IMPLEMENTED`: Database tables do not exist in Drizzle migrations.<br>• `PARTIALLY_IMPLEMENTED`: Tables exist without relational integrity or audit triggers.<br>• `IMPLEMENTED`: Production Drizzle schema with audit triggers.<br>• `VERIFIED_PERSISTENCE`: Transaction rollback and relational constraints tested. |
| **7. End-to-End Status (`E2E`)** | • `NOT_TESTED`: No automated E2E test or manual verification recorded.<br>• `BLOCKED`: Missing dependency (e.g. real database schema, payment gateway) blocks test.<br>• `FAILED`: Automated or manual test failed with regression.<br>• `PARTIALLY_VERIFIED`: Partial journey verified (e.g. mock unit tests pass, preview data renders).<br>• `VERIFIED`: Complete user journey verified from entry to database persistence. |
| **8. Evidence Level (`Evidence`)** | • `NONE`: No evidence available.<br>• `SOURCE_ONLY`: Source code verified on disk.<br>• `SCREENSHOT_CAPTURED`: Genuine screenshot captured from running server instance.<br>• `AUTOMATED_TESTED`: Vitest unit/contract/component test verified passing.<br>• `DEVICE_VERIFIED`: Physically verified on real iOS/Android hardware. |
