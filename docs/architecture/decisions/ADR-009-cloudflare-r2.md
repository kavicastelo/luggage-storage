# ADR-009: Cloudflare R2 for Media, KYC Verification Documents, and Custody Evidence Storage

- **Status:** Accepted
- **Date:** 2026-11-07
- **Phase:** Phase 0A — Product Architecture & System Foundation
- **Related Documents:** [System Architecture Overview](../system-architecture.md), [Backend Domain Architecture Overview](../backend-domain-overview.md)

---

## 1. Context

The platform requires durable, cost-effective, and secure object storage for three very different categories of user-uploaded files identified in the FRS:
1. **Public Marketplace Media (`FR-4 Host Details`, `FR-19 Storage Location Setup`):** Photos of host storefronts and storage areas viewed frequently by browsing travellers.
2. **Confidential Identity & Business Verification Documents (`FR-16 Identity/Business Verification`):** Government IDs, passports, business registration certificates, and utility bills submitted by hosts for platform approval (`FR-17`).
3. **Operational Custody & Incident Evidence (`FR-29 Check-in Evidence`, `FR-41 Incident Reporting`):** Time-sensitive photographs of checked-in bags, physical bag tags, and damaged/unclaimed luggage evidence.

Storing files on the backend server's local filesystem is incompatible with stateless cloud deployment, while traditional cloud object storage (such as AWS S3 without zero-egress agreements) incurs significant bandwidth egress charges as marketplace photo traffic grows.

---

## 2. Decision

We will use **Cloudflare R2** (S3-compatible object storage) paired with **Cloudflare CDN** as the platform's unified file and media storage layer, partitioned into strict security tiers:

1. **Public / CDN-Cached Bucket Tier (`location-media`):**
   - Stores optimized, resized host location photos (`FR-19`).
   - Delivered globally via Cloudflare CDN with zero egress bandwidth fees.
2. **Private / Restricted Bucket Tier (`verification-and-custody-private`):**
   - Stores Host KYC/business verification documents (`FR-16`), check-in luggage evidence photos (`FR-29`), and incident investigation files (`FR-41`).
   - **Never publicly readable.** Files are uploaded and viewed exclusively via short-lived, cryptographically signed URLs generated by the Fastify backend after verifying the caller's role and resource ownership.

---

## 3. Alternatives Considered

1. **Local Disk Storage on the EC2 / VPS Instance:**
   - *Rejected:* Risk of permanent data loss on instance failure; prevents horizontal scaling; couples static media serving to API server CPU/bandwidth.
2. **Standard AWS S3:**
   - *Rejected:* Approved stack locks Cloudflare R2, which provides S3 API compatibility (`@aws-sdk/client-s3`) while eliminating egress bandwidth charges.
3. **Storing Binary Images Directly in PostgreSQL (`BYTEA`):**
   - *Rejected:* Bloats database storage, degrades query cache performance, and increases Neon database backup/compute costs.

---

## 4. Consequences

### Positive
- **Zero Egress Cost:** High-traffic marketplace listing photos (`FR-3`, `FR-4`) are served globally via Cloudflare without per-GB egress fees.
- **S3 API Standard:** Uses standard S3 SDK pre-signed `PUT` and `GET` URLs, keeping the Fastify API server off the heavy binary upload path where appropriate.
- **Strong Privacy Isolation:** Sensitive KYC (`FR-16`) and luggage custody photos (`FR-29`) are strictly isolated from public buckets.

### Negative / Trade-offs
- Requires server-side file validation (MIME type whitelist, maximum file size limits, EXIF stripping/sanitization) before issuing upload permissions or marking uploads complete.

---

## 5. Risks & Mitigations

- **Risk:** Unauthorized access to KYC documents or luggage photos if object keys are guessed or exposed.
  - **Mitigation:** Disable all public access on the private R2 bucket, use unguessable UUIDv4 object keys, and issue pre-signed download URLs with short TTLs (e.g., 5–15 minutes) only after backend RBAC and ownership verification.
